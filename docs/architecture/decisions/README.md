# Step 2 — Architecture Decision Workshop

**Project:** Cited RAG Bot  
**Status:** Proposed for review  
**Version:** 0.1

## Purpose

This folder records the architecture decisions that must be reviewed before HLD and LLD are frozen.

The PRD already locks the product direction: PDF-only V1, multi-PDF collections, hybrid retrieval, reranking, grounded generation, page-level citations, citation validation, evaluation, observability, and controlled no-answer behavior.

Step 2 converts those product requirements into explicit technical decisions.

## Decision Principles

1. Citation provenance must survive every stage from PDF page to final answer.
2. Retrieval quality must be measurable, not assumed.
3. External providers must sit behind interfaces/adapters.
4. PostgreSQL owns durable application metadata; retrieval indexes are derived/searchable artifacts.
5. Long-running ingestion must execute asynchronously.
6. Retrieved PDF content is untrusted data, never trusted instructions.
7. Failure of one retrieval component must have explicitly defined behavior.
8. V1 should be production-oriented without introducing infrastructure that does not materially improve the learning or product goals.
9. Every important architecture choice must be replaceable without rewriting core domain logic.
10. Evaluation design is part of architecture, not a post-build activity.

## Architecture Constraints Derived From PRD

### PDF-only V1

Other document formats are deliberately excluded. Parser abstractions may support future extensions, but no implementation effort should be spent on DOCX, HTML, URLs, or OCR-heavy scanned documents in V1.

### Multi-document collections

Every retrieval operation is scoped to a collection. Every indexed evidence item must preserve at minimum:

- collection_id
- document_id
- document_version
- page_number
- chunk_id
- chunk_order

### Citation integrity

The LLM must never be trusted to invent document IDs, page numbers, or chunk IDs. The application owns citation identity and validation.

### Derived search indexes

Vector/sparse indexes are reconstructable from the durable document/chunk metadata and source PDF. They must not become the only source of provenance truth.

### Evaluation-first architecture

The architecture must expose intermediate retrieval/reranking results so the evaluation harness can measure each stage independently.

## Required Review Questions Before HLD

1. Do we accept Docling as the primary V1 parser, or do we want a lighter parser for the first implementation?
2. Do we accept PostgreSQL + Qdrant as two persistence/search systems, or do we intentionally want a single-store architecture?
3. Do we want sparse retrieval implemented inside Qdrant using sparse vectors/BM25-style representation, or a separate lexical engine?
4. Is Reciprocal Rank Fusion sufficient for V1, with weighted fusion deferred until evaluation proves a need?
5. Should reranking use a local model by default with a provider adapter for hosted rerankers?
6. Should strict retrieval failure fail the query closed, or allow degraded dense-only/sparse-only operation when one retriever is unavailable?
7. Do we accept Redis-backed asynchronous ingestion in V1?
8. Should source PDFs be retained after successful ingestion, and for how long?
9. What authentication boundary do we want for the portfolio version: API key only, or user-level auth?
10. What minimum evaluation thresholds should block a release after the baseline benchmark exists?

## Exit Criteria For Step 2

Step 2 is complete when:

- all ADRs have been reviewed;
- each ADR is marked Accepted, Rejected, or Superseded;
- unresolved choices are explicitly documented rather than hidden in code;
- the accepted decisions are sufficient to produce the HLD without major technology ambiguity.

Do not start application implementation from these ADRs while they remain Proposed. The next output after review is Step 3: HLD.
